# 中断数据解析任务化改造说明

> 本文记录将 BSP 层中断中的协议解析、数据解码等操作迁移到 FreeRTOS 回调任务中的改造方案、实现细节和使用注意事项。

## 1. 改造背景

改造前，外设中断回调中直接调用模块回调，例如：

- USART DMA/IDLE 中断中直接解析遥控器、裁判系统、视觉等协议；
- CAN RX 中断中直接解析电机、超级电容、CANComm 数据；
- USB CDC 中断中直接解析视觉数据；
- SPI/IIC/GPIO EXTI 中断中直接读取传感器并解码。

这会导致：

1. 中断执行时间不可控，协议解析越长，中断延迟越大；
2. 阻塞式传感器读取（如 IST8310 的 IIC 读取）直接占用中断；
3. 多字段结构体在中断和任务之间并发更新，存在数据一致性风险；
4. 高优先级中断被业务解析拖慢，影响系统实时性。

本次改造使用 `bsp/bsp_tools.c` 提供的回调任务机制，把中断处理收缩为“记录数据/入队 + 通知任务”，实际解析放到任务上下文执行。

## 2. 改造范围

已完成两部分：

### 第一阶段

- USART 接收回调任务化；
- USB CDC 接收回调任务化；
- SPI/IIC/GPIO EXTI 回调任务化；
- IST8310 阻塞 IIC 读取从 EXTI 中断迁移到任务。

### 第二阶段

- CAN 接收改为“每总线接收队列 + 接收调度任务”；
- 电机、超级电容、CANComm 等 CAN 数据在任务中解析。

未迁移的内容：

- UART 发送完成中断中的发送队列续传；
- CAN 发送邮箱完成中断中的发送队列续传；
- SPI 发送完成中断中的片选释放；
- PWM DMA 完成回调（主要面向输出，不作为本次输入数据解析对象）；
- UART/CAN 错误中断中的状态恢复逻辑。

这些回调主要承担驱动层状态推进，不属于业务数据解析。

## 3. 总体方案

```text
外设中断
   │
   ├─ 记录长度 / 拷贝数据 / 写入接收队列
   │
   ├─ CallbackTaskNotify()
   │      └─ osThreadFlagsSet()
   │
   └─ 返回，不在中断中解析协议

回调任务
   │
   ├─ osThreadFlagsWait()
   ├─ 调用模块回调
   └─ 清理状态 / 重新启动接收
```

### 3.1 bsp_tools API

`bsp_tools` 的接口调整为：

```c
typedef struct
{
    osThreadId_t thread_id;
    uint32_t signal;
} CallbackTaskHandle_t;

CallbackTaskHandle_t CreateCallbackTask(const char *name,
                                        void (*callback)(void *),
                                        void *argument,
                                        osPriority_t priority,
                                        uint32_t stack_size);

static inline void CallbackTaskNotify(const CallbackTaskHandle_t *handle);
```

`CreateCallbackTask()` 返回任务句柄和线程标志。中断中通过 `CallbackTaskNotify()` 唤醒对应任务。

### 3.2 任务执行机制

回调任务内部循环改为“先等待、后执行”：

```c
for (;;)
{
    osThreadFlagsWait(info->signal, osFlagsWaitAll, osWaitForever);
    info->callback(info->argument);
}
```

这样修复了原实现中任务创建后先空跑一次回调的问题。任务只有在收到信号后才执行回调。

### 3.3 信号位数量

CMSIS-RTOS2 的 FreeRTOS 封装只使用 `bit0~bit30` 作为线程标志，因此最多支持 **31 个回调任务**：

```c
#define CALLBACK_TASK_MAX_COUNT 31U
```

当前工程最多约 28 个 BSP 回调任务，满足限制。创建失败时 `CreateCallbackTask()` 返回空句柄，BSP 会回退到原中断中直接调用回调的方式。

## 4. 各 BSP 改造说明

### 4.1 USART

`USARTInstance` 增加接收帧环形缓冲区：

```c
uint8_t dma_recv_buff[USART_RXBUFF_LIMIT];
USART_RxFrame_t rx_fifo[USART_RX_FIFO_DEPTH];
volatile uint16_t rx_fifo_head;
volatile uint16_t rx_fifo_tail;
volatile uint32_t rx_fifo_overflow;

CallbackTaskHandle_t rx_task;
volatile uint16_t rx_len;
```

`HAL_UARTEx_RxEventCallback()` 现在做：

```c
USART_RxFifoPush(instance, instance->dma_recv_buff, Size);
USARTStartReceive(instance);       // 立即重新启动 DMA
CallbackTaskNotify(&instance->rx_task);
```

回调任务中执行：

```c
while (USART_RxFifoPop(instance, &frame_length))
{
    instance->rx_len = frame_length;
    module_callback();
}
```

**数据策略**：DMA 每次收完一帧后立即重启，整帧先进入 `rx_fifo`；任务再从队列取出完整帧并解析。环形槽位为 4，可用容量为 3 帧（保留一个空槽区分满/空），队列满时丢弃最新帧并记录 `rx_fifo_overflow`。模块回调仍然读取 `recv_buff`，不需要修改；应用层也不需要修改。详细说明见 [USART 接收环形缓冲区与中断任务化改造详解](./USART中断数据解析任务化改造详解.md)。

### 4.2 USB CDC

`CDC_Receive_FS()` 不再直接调用模块回调，而是调用：

```c
USBRxEvent(Buf, *Len);
```

`USBRxEvent()` 只把本次 USB 传输的数据追加到 2KB 字节环形缓冲区，然后通知 `usb_rx` 任务。任务中调用模块注册的 `rx_cbk(available)`，模块通过 `USBAvailable()`/`USBRead()` 读取字节流并自行按协议拆帧。

**数据策略**：USB CDC 是字节流，一次 USB 传输可能只包含半帧，也可能包含多帧，因此拆帧放在模块层完成。接收环形缓冲区空间不足时整包丢弃并置溢出标志，任务清空缓冲区后以 `rx_cbk(0)` 通知模块复位解析状态。

发送方向使用 512B 环形缓冲区，`USBTransmit()` 只负责入队，`CDC_TransmitCplt_FS()` 触发续发，避免 `USBD_BUSY` 时静默丢包，也允许调用者使用栈上的临时缓冲区。

### 4.3 CAN

每条 CAN 总线新增独立的接收队列：

```c
typedef struct
{
    CAN_FIFO_Data_s queue[32];
    volatile uint8_t front_idx;
    volatile uint8_t back_idx;
    volatile uint8_t current_size;
    volatile uint32_t drop_cnt;
    CallbackTaskHandle_t task;
} CAN_Rx_FIFO_s;
```

中断中：

1. 从 CAN FIFO 取出原始帧；
2. 匹配 `rx_id` 找到对应 `CANInstance`；
3. 将原始数据写入每总线接收队列；
4. 通知该总线的接收任务。

任务中出队、拷贝到 `CANInstance.rx_buff`，再调用 `can_module_callback()`。

**数据策略**：队列深度 32 帧，队列满时丢弃最旧帧并记录溢出计数。相比“每个 CAN 实例一个任务”，每总线一个任务减少了任务数量，并保持帧到达顺序。

### 4.4 SPI/IIC

`SPIInstance` 和 `IICInstance` 增加 `callback_task`。

- SPI 接收完成中断中先释放片选，再通知任务；
- IIC 接收完成中断中直接通知任务；
- 模块解析回调在任务上下文执行。

这样 SPI/IIC 的传感器数据解析不再占用中断时间。

### 4.5 GPIO EXTI

`GPIOInstance` 增加 `callback_task`。EXTI 中断只通知任务，模块的 EXTI 回调在任务中执行。

典型收益：

- IST8310 的 `IST8310StartTransfer()` 中阻塞 IIC 读取现在运行在任务中；
- BMI088 的 EXTI 回调中 SPI 读取/解码不再运行在中断上下文中。

BMI088 的 SPI/GPIO 回调改为在 `SPIRegister()` / `GPIORegister()` 之前配置，确保注册时能够创建对应的回调任务。

## 5. 启动流程与 FreeRTOS 配置调整

### 5.1 启动顺序

`osKernelInitialize()` 提前到 `RobotInit()` 之前：

```c
osKernelInitialize();
RobotInit();
MX_FREERTOS_Init();
osKernelStart();
```

这样 BSP 在模块注册阶段创建回调任务时，内核已经完成初始化。

### 5.2 中断开启时机

`RobotInit()` 不再在结尾调用 `__enable_irq()`，中断保持关闭，直到 FreeRTOS 启动第一个任务时由移植层统一开启。

这样可以避免调度器启动前外设中断调用 `osThreadFlagsSet()`，触发尚未完全启动的调度器。

### 5.3 FreeRTOS 配置

| 配置 | 值 | 说明 |
|---|---:|---|
| `configTOTAL_HEAP_SIZE` | 65536 | 为回调任务预留堆空间 |
| `CALLBACK_TASK_DEFAULT_STACK_SIZE` | 1024 | 回调任务默认栈大小 |
| `configCHECK_FOR_STACK_OVERFLOW` | 2 | 开启栈溢出检查 |
| `configUSE_MALLOC_FAILED_HOOK` | 1 | 开启内存分配失败钩子 |
| `configUSE_TASK_NOTIFICATIONS` | 1 | 线程标志依赖任务通知 |

同时增加：

- `vApplicationStackOverflowHook()`
- `vApplicationMallocFailedHook()`

### 5.4 回调任务优先级

当前 BSP 回调任务统一使用 `osPriorityAboveNormal`，确保数据解析优先于普通业务任务，同时解析任务执行时间较短，不会长期占用 CPU。

## 6. bsp_tools 命名整理

本次同时整理了 `bsp_tools` 中的缩写命名：

| 旧名称 | 新名称 |
|---|---|
| `MX_SIG_LIST_SIZE` | `CALLBACK_TASK_MAX_COUNT` |
| `sig_idx` | `callback_task_count` |
| `cbkinfo_list` | `callback_task_info_list` |
| `CallbackTaskInfo_t.ins` | `CallbackTaskInfo_t.argument` |
| `CallbackTaskBase` | `CallbackTaskEntry` |
| 参数 `cbk` | `callback` |
| 参数 `ins` | `argument` |
| 日志标签 `cbk_register` | `callback_task` |

函数名 `CreateCallbackTask()`、`CallbackTaskNotify()` 保持不变，调用方无需修改。

## 7. 资源占用

最近一次全量构建结果：

```text
RAM:   91144 B / 128 KB (69.54%)
FLASH: 107080 B / 512 KB (20.42%)
```

新增资源主要来自：

- FreeRTOS heap 从 20KB 增加到 64KB；
- 每个回调任务默认 1KB 栈；
- USB 接收环形缓冲区 2048B、发送环形缓冲区 512B；
- 每总线 CAN 接收队列 32 帧；
- 每个 USART 实例新增约 1.3KB 接收帧队列（运行时由 newlib 堆分配，不计入静态 RAM 统计）。

任务栈实际静态分析值较低：

- `USARTDeferredRx`：40B
- `USBDeferredRx`：24B
- `CANRxTask`：48B
- 模块回调如 `DecodeVision` / `DecodeDJIMotor` / `JudgeReadData`：约 16~32B

1KB 栈对当前回调链路有足够余量，仍建议上板后通过 `osThreadGetStackSpace()` 或高水位接口确认。

## 8. 验证方式

### 已完成

- `cmake --build build/Debug --clean-first` 全量构建通过；
- 检查 ISR 中不再直接调用业务解析回调；
- 检查所有 `CreateCallbackTask()` 调用点均有失败回退路径；
- 检查回调任务栈使用情况。

### 建议上板验证

1. 遥控器 USART3 数据持续更新，daemon 不误报离线；
2. 裁判系统 USART6 数据持续更新，UI 正常刷新；
3. USB 视觉数据持续更新，丢帧率可接受；
4. CAN 电机反馈、超级电容数据正常，电机控制无异常；
5. 开启 `configCHECK_FOR_STACK_OVERFLOW` 后长时间运行不进入溢出钩子；
6. 通过 `xPortGetFreeHeapSize()` 检查运行期 heap 余量；
7. 在最高通信频率下观察 USART/CAN/USB 的丢帧情况。

## 9. 已知限制与注意事项

1. **USART 帧队列满时丢弃最新帧**：环形槽位为 4，可用容量为 3 帧；连续高负载下可能丢帧，可通过增大 `USART_RX_FIFO_DEPTH` 或提高任务优先级缓解。
2. **USB 接收溢出时整包丢弃**：USB 接收环形缓冲区空间不足时置溢出标志并通知模块复位解析状态，视觉数据需要保证处理速度。
3. **CAN 队列满时丢弃最旧帧**：极端负载下可能破坏多帧协议，可通过增大 `CAN_RX_FIFO_SIZE` 或降低总线负载解决。
4. **最多 31 个回调任务**：受 CMSIS-RTOS2 线程标志位限制，超过后创建失败并回退到中断处理。
5. **回调任务中不要阻塞**：当前任务优先级较高，长时间阻塞会影响其他任务。IST8310 等阻塞式传感器读取已放入任务，但传感器异常时仍需关注超时时间。
6. **BMI088 触发模式原有异步链路未完整重写**：本次只将回调移出中断，若启用该模式仍需单独验证 SPI DMA 完成后的数据解析时序。
7. **CubeMX 重新生成**：`main.c` 中 `osKernelInitialize()` 的位置、`usbd_cdc_if.c` 的用户代码段、`FreeRTOSConfig.h` 中手工添加的配置需要在重新生成后复查。
